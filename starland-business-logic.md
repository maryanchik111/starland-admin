# Starland — фінальний план (для передачі агенту в IDE)

Контекст: одна конкретна школа (Starland), приватна, не держзамовлення. Single-tenant,
без розрахунку на мультитенант у майбутньому. Соло-розробник (ти) + AI-агенти
(Claude Code та інші). Термін MVP — 1 місяць.

Цей документ фіксує **рішення**, а не варіанти. Там, де рішення приймав я (агент) за
браком твоєї явної відповіді — позначено окремо з обґрунтуванням, щоб ти міг
скоригувати за потреби.

---

## 0. Модель продукту

- **Single-tenant**, одна школа Starland. `school_id` в схему **не закладаємо** —
  спрощує модель даних і RLS-політики (менше джойнів, менше шансів забути перевірку).
  Якщо колись знадобиться друга школа — це буде окремий деплой (окрема БД), а не
  розширення однієї бази.
- Дві організаційні ролі на старті адмінських прав: **ти** (розробник, обмежений
  доступ) і **директор** (повний адмін школи). Директор далі сам створює/призначає
  права іншим співробітникам через адмінку.

---

## 1. Хостинг та інфраструктура

- **Vercel + Supabase (Варіант A)** — керований хостинг, без власного VPS.
  Обґрунтування: ти соло, підтримувати власний сервер (патчі ОС, бекапи, моніторинг)
  — це постійний час, якого при місячному дедлайні немає. Supabase дає RLS,
  auth, storage, realtime "з коробки".
- **Регіон Supabase: EU (eu-central)** — дефолт для приватної школи, GDPR-сумісно.
  Змінити регіон пізніше без міграції неможливо, тож фіксуємо це зараз свідомо.
- **Realtime/чат: Supabase Realtime**, а не окремий Socket.io-сервіс.
  *Це моє рішення на "як краще?" (п.6):* при соло-розробнику і вже обраному Supabase
  окремий realtime-процес — це зайвий деплой, зайва інфраструктура для підтримки,
  і Supabase Realtime вже вміє слухати зміни в Postgres напряму (через logical
  replication) без окремого pub/sub шару. Якщо навантаження зростатиме і з'являться
  ліміти Supabase Realtime — тоді вже мігруємо на окремий сервіс, не раніше.
- **Postgres/Supabase без прямого публічного доступу** з клієнта — усе через
  Supabase client + RLS, ніякого прямого підключення з фронтенду сирими кредами.
- Моніторинг: Sentry (помилки) з першого релізу. Grafana/Better Stack — коли
  з'явиться реальне навантаження, не блокує MVP.

## 2. Технологічний стек (остаточно)

| Шар | Вибір |
|---|---|
| Frontend + API | Next.js (App Router), Server Actions для мутацій |
| БД | Supabase Postgres, RLS |
| ORM | **Prisma** |
| Auth | **Supabase Auth** (email+password, MFA/TOTP з коробки, passkeys підтримуються) |
| Realtime/чат | **Supabase Realtime** |
| Файли | **Supabase Storage** (приватні бакети, підписані URL з коротким TTL) |
| Черги/фонові задачі | BullMQ + Redis (Upstash Redis, managed) — нагадування, звіти, дедлайни ДЗ |
| Хостинг | Vercel (два проєкти: portal + admin) |
| Моніторинг | Sentry |

Примітка: Prisma + Supabase — ORM працює через прямий connection string
(рекомендовано Supabase Connection Pooler / PgBouncer, бо Vercel serverless
functions відкривають багато коротких з'єднань).

## 3. Portal / Admin — розділення (уточнено)

- Два окремі Next.js-застосунки в монорепо: `apps/portal` (**тільки батьки й учні**)
  і `apps/admin` (**директор/адмін і вчителі**), спільна Prisma-схема в `packages/db`.
- Тобто межа розділення проходить не по "хто дивиться / хто редагує", а по
  "хто персонал школи, а хто ні": вчитель виставляє оцінки, відмічає
  відвідуваність, спілкується в чаті — усе це робить з того самого застосунку,
  що й директор, просто з обмеженим за роллю набором прав (тільки свої
  предмет+клас, без доступу до налаштувань школи, керування ролями тощо).
- Практично це означає:
  - `apps/admin` отримує повноцінний RBAC усередині себе (директор ≠ вчитель за
    правами, хоч і той, і той — в одному застосунку).
  - Захист адмін-домену (Cloudflare Access, passkeys, нейтральний піддомен)
    тепер стосується **всього персоналу школи, включно з вчителями**, не тільки
    директора/адміністратора. Це підвищує кількість людей, які проходять через
    Cloudflare Access allowlist — варто одразу зробити цей allowlist по
    шкільному email-домену (а не список вручну введених адрес), щоб не
    підтримувати список окремо.
  - `apps/portal` лишається максимально простим і "легким" за вимогами до
    UX (без passkeys, без коротких сесій, без Cloudflare Access) — тільки
    батьки й учні, довший TTL сесії, звичайний email+password (2FA опційна).
- Два окремі Vercel-проєкти з одного git-репо, кожен зі своїм Root Directory.
- **Домен адмінки — додатковий шар прихованості** (п.11): не `admin.starland.com`,
  а нейтральний піддомен без очевидного зв'язку зі школою на окремому кореневому
  домені. Це не заміна автентифікації, а додатковий шар — сам по собі "невідомий
  домен" не захист (світиться в Certificate Transparency logs), тому робимо
  разом з наступним пунктом.
- **Захист адмінки: Cloudflare Access (Zero Trust)** з allowlist по email-домену
  школи (п.12, перший варіант). Пояснення простими словами: перед тим, як людина
  взагалі побачить сторінку логіну адмінки, Cloudflare перевіряє, що вона входить
  зі свого корпоративного/шкільного email (через одноразовий код на пошту).
  Не знає такого email — не бачить навіть форму входу. Це шар *перед* твоєю
  автентифікацією (Supabase Auth + MFA йде вже після).
- Preview-деплої Vercel для `apps/admin` — обов'язково увімкнути Vercel
  Authentication (Deployment Protection), інакше preview URL публічно доступний
  в обхід Cloudflare.
- Supabase: `admin` не отримує "ширший" anon key — привілейовані операції йдуть
  через Postgres-функції з `SECURITY DEFINER`, а не голий `service_role key`.

## 4. Автентифікація та доступи

- **Публічної реєстрації немає ніде** — підтверджено. Акаунти вчителів створює
  директор/адмін, акаунти батьків — через invite-код при зарахуванні дитини.
- **Персонал (вчителі/адміни): passkeys/WebAuthn** як основний метод (п.13,
  підтверджено) — стійкіший за SMS (без ризику SIM-swap). TOTP як запасний варіант.
- **Батьки: 2FA опційна**, але UI рекомендує її увімкнути (банер/нагадування при
  першому вході, не блокуюче).
- **Адмінські права**: старт — ти + директор. Директор далі сам роздає ролі й
  права іншим співробітникам через адмін-панель (потрібен буде інтерфейс
  керування ролями/дозволами, не тільки бінарне "адмін/не адмін").
- **Break-glass акаунт для розробника**: так, підтверджено. Окремий тимчасовий
  акаунт для екстреного доступу до прод-даних, з посиленим логуванням, що
  деактивується одразу після використання. В штатному режимі ти (розробник) не
  маєш постійного прямого доступу до прод-БД — працюєш через staging.

## 5. Шифрування даних

- **At-rest шифрування диска** — базовий рівень, забезпечує Supabase з коробки
  (підтверджено, п.18).
- **Медичні дані дітей — окреме питання.** Ти сказав "можливо" (п.19). Це важливо
  уточнити до розробки схеми:
  - Якщо школа збирає медичні дані дітей (алергії, хронічні стани, що потрібно
    вчителям на випадок ситуації) — це категорія даних з підвищеною чутливістю
    за законом, і для неї варто зробити **application-level шифрування колонок**
    (`pgcrypto`/`pgp_sym_encrypt`), з ключем окремо від бази (Supabase Vault або
    інший secrets-менеджер), а не покладатись тільки на at-rest.
  - Якщо медичних даних не буде взагалі (тільки навчальні дані: оцінки, ДЗ,
    відвідуваність) — at-rest достатньо, і колонкове шифрування не потрібне.
  - **Рекомендація:** закласти в схему поле для медичних нотаток як опціональне
    і зашифроване з самого початку (дешевше зробити зараз, ніж мігрувати потім),
    навіть якщо на MVP воно порожнє для всіх учнів.
- Файли/вкладення (фото, документи) — приватні Supabase Storage бакети + підписані
  URL з коротким TTL (~5 хв), не публічні лінки.

## 6. Бізнес-логіка — оцінки

- Вчитель ставить оцінку тільки в межах своєї пари предмет+клас.
- **Вікно редагування — 48 годин**, підтверджено.
- **Права адміна (п.21, уточнено твоєю відповіддю):** адмін має право в будь-який
  момент змінити або скасувати (soft-delete) оцінку, яку поставив вчитель, і
  навпаки — вчитель бачить, якщо адмін це зробив. Це не одностороннє
  "адмін перекриває вчителя назавжди", а взаємна видимість змін:
  - Кожна зміна (вчителем чи адміном) обов'язково пише запис в `audit_logs`:
    хто, коли, що саме змінив, стара/нова оцінка.
  - Зміна адміном оцінки поза вікном 48 год — обов'язковий коментар-причина
    (вже було в бізнес-логіці, залишаємо).
  - Оцінка ніколи не видаляється фізично — тільки soft-delete з причиною.
  - UI має явно показувати учню/батькам, якщо оцінку востаннє змінював не
    оригінальний вчитель (прозорість — важливо для довіри, як у прикладі з Мрії).

## 7. Бізнес-логіка — чат

- **Учень ↔ вчитель напряму — дозволяємо** (підтверджено, п.22), без окремого
  прапорця "школа забороняє" — раз ти дозволяєш, робимо це доступним одразу,
  без додаткової настройки на рівні школи (бо школа тут одна і рішення вже прийнято).
- **Адмін має доступ до всіх чатів**, включно з soft-deleted повідомленнями —
  це модерація/захист дітей, не "стеження" (узгоджено з підходом Мрії з аналізу
  конкурентів).
- **Rate-limit на повідомлення — на розсуд агента (п.23):** старт — **20
  повідомлень/хвилину на користувача**. Це достатньо для живого спілкування в
  класному чаті, але відсікає флуд/спам-скрипти. Легко підкрутити після
  спостереження за реальним використанням.
- **Шифрування чату — так, шифруємо** (підтверджено, п.24). Уточнення: на MVP
  реалістичний рівень — TLS в транзиті (обов'язково) + шифрування вмісту
  повідомлень на рівні застосунку перед записом у БД (AES-256-GCM, ключ окремо
  від бази), а не повноцінний E2E-протокол (Signal-подібний) — той вимагає
  керування ключами на клієнті й серйозно ускладнить read receipts/модерацію
  адміном. Якщо потрібен саме E2E — це окрема розмова, бо він конфліктує з
  вимогою "адмін бачить усі чати для захисту дітей" (E2E за визначенням ховає
  вміст навіть від сервера).

## 8. Офлайн-режим

- **Переноситься на пізнішу фазу** (підтверджено, п.25) — не блокує MVP.
  MVP працює тільки онлайн.
- **Конфлікт-резолюція, коли дійдемо до офлайну (п.26, на розсуд агента):**
  - Читання (оцінки/розклад/ДЗ) — last-write-wins від сервера, просто
    перезаписуємо локальний кеш.
  - Чат — дедуплікація по `client_id`, порядок за серверним `created_at`.
  - **Оцінки/відвідуваність — ручне вирішення конфлікту адміном**, не auto-overwrite.
  Обґрунтування: оцінка — це юридично значуща дитяча дані, тиха автоматика тут
  небезпечна (можна незворотньо загубити реальну виставлену оцінку). Це
  узгоджується з тим, що вже написано в `business-logic-security-offline.md`.

## 9. Юридичні аспекти

- **Згода батьків**: батьки надають згоду (спосіб отримання — поза системою,
  на розсуд школи), **адмін вносить факт згоди в карту учня** — потрібне поле
  типу `parental_consent_given: bool + date + entered_by` в профілі учня, а не
  просто чекбокс при реєстрації батьків (бо реєструє акаунти адмін, не сам батько).
- **DPA** — це наш план, тобто ми документуємо, з ким потрібен DPA (Vercel,
  Supabase) і готуємо шаблон/чекліст, але підписання — окремий організаційний крок
  зі школою, не код.
- **Retention policy: 5 років** зберігання даних випускника після завершення
  навчання, з можливістю змінити термін пізніше (тобто термін — конфігурований
  параметр у налаштуваннях школи, не хардкод у коді).

## 10. Інтеграція з системою кухні

Уточнено: інтеграція потрібна **одразу, в MVP**, не пізніше. Модель — портал
(батьки/учні) робить запис через API в базу кухні (напр. замовлення/відміна
харчування), кухня — окрема, вже готова система зі своєю БД.

### 10.1 Архітектура інтеграції

- **Це не спільна БД і не спільний код** — Starland і кухня лишаються двома
  окремими системами. Portal викликає **API кухні** (сервер-до-сервер), кухня
  ніколи не отримує прямого доступу до бази Starland і навпаки.
- Виклик робиться **тільки з бекенду** (Next.js Server Action / Route Handler
  в `apps/portal`), ніколи з клієнтського коду в браузері — ключ/токен до API
  кухні не повинен потрапляти в клієнтський бандл (аналогічно правилу з
  `SUPABASE_SERVICE_ROLE_KEY` — тримати тільки на сервері).
- Дані, які йдуть у запиті до кухні, — мінімальний, суворо typed payload
  (напр. `student_id`, `meal_date`, `action`), провалідований через Zod
  **перед** відправкою. Кухня не повинна отримувати нічого зайвого "про запас".

### 10.2 Головна вимога — ізоляція від адмінки школи

Ти хочеш, щоб цей стик не міг стати шляхом з `portal` в `admin`. Це вирішується
не одним засобом, а кількома незалежними шарами:

1. **Окремий, максимально вузький API-ключ/токен для кухні**, який має право
   *тільки* писати замовлення харчування — не читати оцінки, не читати
   персональні дані понад необхідне, не мати доступу до жодного admin-ендпоінту.
   Якщо кухня видає API-ключі з ролями/скоупами — брати найвужчий можливий scope.
2. **Кухонний інтеграційний код фізично живе тільки в `apps/portal`**, не в
   `apps/admin`. У `apps/admin` немає навіть коду, який знає про існування
   кухонного API — так навіть теоретична вразливість в інтеграції не має шляху
   до адмінського застосунку, бо його там просто немає.
3. **Немає зворотного виклику з кухні в Starland**, який міг би щось міняти.
   Якщо кухні потрібно повідомити щось назад (статус оплати, скасування) —
   це окремий вебхук-ендпоінт в `apps/portal` з власною HMAC-підписаною
   перевіркою (перевіряємо, що запит справді від кухні, за секретом, не за IP
   чи доменом), і цей ендпоінт може **тільки** оновлювати статус замовлення
   харчування — ніяких прав на запис у таблиці оцінок/чатів/користувачів.
4. **Rate-limit і валідація на цьому ендпоінті** так само, як і на решті API —
   він не привілейований лише тому, що зовнішній.
5. **Кухонний токен зберігається окремо** (Vercel Env Var, scope тільки на
   проєкт `portal`, не видно `admin`-проєкту в Vercel Environment Variables).
6. **Аудит-лог на кожен запис у кухню** (хто, коли, яке замовлення) — так само,
   як і решта критичних дій, щоб було видно, якщо щось пішло не так.

Підсумок: навіть у гіршому випадку — якщо кухонний API-ключ *раптом* витече —
максимум, що можна зробити цим ключем, це створити/скасувати замовлення
харчування. Він фізично не дає доступу ні до чого в `apps/admin`, ні до Supabase
service role, ні до інших таблиць Starland.

### 10.3 Що уточнити з боку кухонної системи

- Чи кухня видає API-ключі зі scoped-правами (тільки запис замовлень), чи один
  "повний" ключ на все — якщо тільки повний, варто попросити в них розвести це,
  або обмежити payload на своєму боці максимально жорстко.
- Чи є в кухні свій rate-limit/захист від зловживань з їхнього боку (щоб не
  єдиною точкою відмови була тільки наша сторона).
- Формат аутентифікації запиту (API key в header, HMAC, OAuth) — визначає, як
  саме реалізовувати п.10.2.3.

## 11. AI-модуль

- Залишається як **майбутня фаза**, не в MVP (підтверджено, п.31). Проєктуємо
  архітектуру так, щоб AI-сервіс міг пізніше читати ті самі таблиці окремим
  сервісом, не блокуючи базовий продукт (як у моделі TGI Platform — базовий tier
  окремо від AI-tier).

## 12. Прогалини проти конкурентів

- Оплати/харчування/інвентаризація — закриваємо через ізольовану API-інтеграцію
  з вашою готовою кухонною системою одразу в MVP (розділ 10).
- Мобільний застосунок (є в nz.ua) — не в MVP, PWA пізніше може частково закрити
  цю потребу, коли дійдемо до офлайн-фази.

## 13. Область MVP на 1 місяць (соло + AI-агенти)

Реалістичний скоуп, з огляду на дедлайн і команду з однієї людини + агентів:

**Входить в MVP:**
- Supabase (Postgres + Auth + Storage + Realtime), Prisma-схема
- Portal (батьки/учні) + Admin (директор/адмін/вчителі) як два окремі
  Next.js/Vercel застосунки
- Ролі: учень, батько — у `portal`; вчитель, адмін (директор) — у `admin`, без
  гнучкого RBAC-конструктора на старті — простий рольовий доступ, керування
  правами директором можна спростити до "призначити роль користувачу" в MVP,
  повноцінний UI для гнучких прав — вже наступна ітерація
- CRUD: класи, предмети, учні, вчителі, зарахування
- Журнал: оцінки (з логікою 48-год вікна + adмінські права + audit log), ДЗ,
  відвідуваність
- Чат (учень/батько/вчитель, груповий класний, адмін бачить усе) через Supabase
  Realtime, rate-limit 20/хв, шифрування вмісту повідомлень
- 2FA/passkeys для персоналу, invite-based реєстрація, Cloudflare Access перед
  admin-доменом
- Базовий audit log на критичні дії
- Supabase EU-регіон, приватні Storage-бакети
- **Інтеграція з кухнею** (замовлення/відміна харчування) — тільки з `apps/portal`,
  ізольована від `apps/admin` за принципами з розділу 10

**Не входить у MVP (наступні фази):**
- Офлайн-режим (PWA/IndexedDB/outbox)
- AI-модуль/персоналізація
- Мобільний застосунок
- Гнучкий RBAC-конструктор ролей (тільки базовий на MVP)
- Пентест/зовнішній аудит (робимо після першого робочого релізу)

## 14. Відкриті питання, які варто закрити до/під час розробки

Ці пункти не блокують старт, але краще визначитись найближчим часом:

1. **Медичні дані дітей** — чи справді збираються (алергії, хронічні стани)?
   Від відповіді залежить, чи робимо колонкове шифрування зараз чи ні (розділ 5).
2. **Формат отримання згоди батьків** — паперово на зборах, чи є якийсь цифровий
   слід, який адмін потім вносить у систему (розділ 9)?
3. **Формат аутентифікації API кухні** (API key / HMAC / OAuth) і чи є в кухні
   scoped-ключі — треба уточнити з їхнього боку перед реалізацією (розділ 10.3).
