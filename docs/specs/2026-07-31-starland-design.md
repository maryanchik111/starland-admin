## 1. Архітектура застосунків

Монорепо (pnpm workspaces + Turborepo), три Vercel-проєкти з одного репозиторію:

| Застосунок | Аудиторія | Захист входу |
|---|---|---|
| `apps/admin` | персонал школи | Cloudflare Access (allowlist за шкільним доменом) → Supabase Auth + passkeys/TOTP |
| `apps/portal` | родинні акаунти | Supabase Auth, email+пароль, 2FA опційна, довший TTL сесії |
| `apps/api` | машинний трафік | HMAC-підписи, статичні токени. Сесій немає взагалі |

`apps/api` існує, щоб машинний вхід (webhook сканера, webhook кухні, webhook
Telegram, ICS-фіди, cron-ендпоінти) не вимагав винятків у Cloudflare Access перед
адмінкою. Виняток у цьому шарі знецінює сам шар.

### Пакети

```
packages/
  db/            Prisma-схема, міграції, RLS-політики, сіди, перф-фікстури
  domain/        бізнес-логіка без залежності від Next.js
  auth/          сесії, обчислення дозволів, guard-и
  notifications/ рушій подій → каналів (Telegram, email)
  integrations/
    scanner/     клієнт і контракт подій сканера
    kitchen/     клієнт кухні — імпорт дозволений лише з portal і api
  ui/            спільні компоненти
  i18n/          українські тексти
  exports/       генерація .xlsx і .docx
```

Ізоляція кухні з розділу 10 старого документа стає машинно-перевірюваною:
ESLint-правило меж забороняє `apps/admin` імпортувати `integrations/kitchen`.
Правило прозою живе до першого поспіху.

### Фонові задачі

BullMQ + Redis скасовано: воркер вимагає постійного процесу, якого на Vercel
немає. Замість нього — **transactional outbox**:

1. Доменна зміна і запис у `outbox` — в одній транзакції.
2. Гарячий шлях (вхід у школу, нова оцінка) одразу штовхає задачу в QStash з
   ендпоінта, що обробив подію. Затримка — секунди, не хвилини.
3. Vercel Cron (щохвилини) — **страхувальна мітла**: підбирає рядки `outbox`,
   яких ніхто не забрав. Cron не є основним шляхом доставки.

Це прямо відповідає на ризик гранулярності cron: критична латентність не
залежить від розкладу. Потрібен Vercel Pro — на Hobby cron обмежений добовим
інтервалом і двома задачами.

Порядок доставки QStash не гарантує. Тому кожна подія несе `event_seq` у межах
свого агрегату, а споживач відкидає застарілу (last-write-wins за `event_seq`).
Для сповіщень строгий порядок і не потрібен — потрібна відсутність дублів, див. §7.

## 2. Модель доступів

### Таблиці

`roles`, `permissions`, `role_permissions`, `user_roles`, `permission_grants`.

`permission_grants` — персональні винятки: `user_id`, `permission_id`,
`effect (allow|deny)`, `scope_type (global|class|subject|student)`, `scope_id`,
`granted_by`, `reason`, `expires_at`, `revoked_at`. Deny перемагає allow.
Фізичного видалення немає; створення й відкликання пишуть `audit_logs`.

### Продуктивність RLS

Наївне `has_permission(auth.uid(), 'grades.read', 'class', grade_entries.class_id)`
у політиці обчислюється **на кожен рядок**, бо аргумент змінюється по рядках.
`STABLE` тут не рятує: кешування спрацьовує лише за незмінних аргументів.

Рішення — проєкція ефективних прав:

- Таблиця `user_effective_scopes(user_id, permission_code, scope_type, scope_id)`,
  що підтримується тригерами на `user_roles`, `role_permissions`,
  `permission_grants`, `teaching_assignments`, `enrollments`.
- RLS-політика перетворюється на перевірку входження в множину:
  ```sql
  USING (
    class_id IN (
      SELECT scope_id FROM user_effective_scopes
      WHERE user_id = auth.uid()
        AND permission_code = 'grades.read'
        AND scope_type = 'class'
    )
  )
  ```
  Підзапит не залежить від рядка, тому виконується один раз (InitPlan), а не
  N разів. Індекс: `(user_id, permission_code, scope_type)`.
- Допоміжні функції — `STABLE SECURITY DEFINER`, інакше політика на таблицях
  доступів рекурсивно викликає саму себе.
- Варіант із `current_setting()` відхилено: сесійні змінні ненадійні за
  транзакційного пулінгу PgBouncer, який ми змушені використовувати через
  serverless. Транзакційно-локальний `set_config` працює, але вимагає обгортати
  геть кожен запит у транзакцію — забудеться в першому ж місці.

**Перф-бюджет як частина Т1, не «потім»:** фікстура на 350 учнів × 2 навчальні
роки (~400 тис. `grade_entries`, ~600 тис. `attendance_records`) і тест, що
падає, якщо вибірка журналу класу за семестр перевищує 200 мс.

### Підключення до бази — від нього залежить, чи діє RLS взагалі

PostgreSQL **не застосовує RLS до суперкористувачів і власників таблиць**.
Тому підключення, яким працює застосунок, вирішує, чи політики є примусом, чи
декорацією. Розділяємо два підключення:

| Змінна | Роль | Для чого |
|---|---|---|
| `DATABASE_URL` | `postgres` (суперкористувач) | Тільки міграції, сіди й локальні інструменти |
| `APP_DATABASE_URL` | `app_runtime` — `nosuperuser`, `nobypassrls` | Увесь рантайм застосунку |

Користувацький контекст задається на рівні транзакції, а не зʼєднання — інакше
він протікає між запитами через пулер:

```ts
withUserContext(authUserId, async (tx) => { /* запити */ })
// всередині: set_config('request.jwt.claims', …, true) + set local role authenticated
```

Це той самий механізм, яким користується тестовий стенд RLS. Спільний механізм —
навмисно: тест, який проходить, доводить поведінку продакшену, а не власну.

Привілейовані операції (сіди, фонові задачі, обслуговування) свідомо йдуть повз
RLS через `DATABASE_URL` — але кожне таке місце має бути явним і перелічним, а не
випадковим наслідком того, що всі підключення однакові.

### Прозорість прав

Екран «ефективні права людини» показує кожен дозвіл із походженням: з ролі
`Вчитель`, чи персональний грант від директора з датою й причиною. Будується з
тієї самої проєкції `user_effective_scopes`, що виконує перевірку, — тому UI не
може розійтися з реальним доступом. Без цього через два роки ніхто не пояснить,
чому конкретний вчитель раптом не бачить клас.

### Ролі-сіди

`director`, `deputy_director`, `admin`, `secretary`, `teacher`, `mentor`,
`assistant`, `psychologist`, `speech_therapist`, `nurse`, `developer`,
`student_family`.

## 3. Ідентичність родин

- Один акаунт на учня. Дані дитини, батьків і опікунів — у профілі учня.
- `linked_accounts(owner_user_id, student_id, linked_by, created_at)` — родина з
  кількома дітьми входить один раз і перемикає дитину.
- **Активна дитина не зберігається в JWT і не приходить із клієнта як дозвіл.**
  `student_id` у запиті — це намір. Перевірка належності виконується в RLS:
  ```sql
  student_id IN (SELECT student_id FROM linked_accounts WHERE owner_user_id = auth.uid())
  ```
  IDOR неможливий за побудовою, а перемикання дитини не потребує перевипуску
  токена (що було б проблемою при кожному перемиканні).
- `telegram_links(user_id, chat_id, label, linked_at)` — кілька привʼязок на
  акаунт (мама, тато, дитина), у кожної власна матриця подій.

## 4. Схема БД

### 4.1 Доступи
`users`, `roles`, `permissions`, `role_permissions`, `user_roles`,
`permission_grants`, `user_effective_scopes`, `linked_accounts`,
`telegram_links`, `notification_preferences`.

### 4.2 Школа
`academic_years`, `academic_periods` (семестри), `classes`, `subjects`, `rooms`,
`bell_slots` (розклад дзвінків; дозволяє окремі тривалості для 1 класу),
`academic_calendar` (канікули, свята, дистанційні дні).

### 4.3 Учні
- `students` — ПІБ, дата народження, фактична адреса, статус.
- `student_health` — **структуровані поля без шифрування**, базовий набір:
  група здоровʼя, фізкультурна група, коди алергій (довідник `allergy_types`),
  хронічні стани (довідник), обмеження для фізичних навантажень.
  За цим потрібні фільтри й звіти, тому вони не шифруються.
- `student_health_notes` — вільний текст (анамнез, коментарі лікаря),
  **зашифрований**, доступ за окремим дозволом, читання логується.
- `student_critical_note` — короткий текст, видимий будь-якому вчителю
  («алергія на арахіс — епіпен у медкабінеті»). Свідомо не під замком: у
  критичній ситуації немає часу шукати того, у кого є дозвіл.
- `guardianships` — `student_id`, `person_id`, `relation`,
  `is_legal_representative`, `can_pick_up`, `receives_notifications`.
- `student_measurements` — часовий ряд (дата, ріст, вага, хто вніс). Без історії
  порівняння початку й кінця року неможливе.
- `student_documents` — довідки й файли у приватному бакеті.
- `person_cards(person_id, qr_code, valid_from, valid_to)` — привʼязка номера QR
  до людини. Номер закріплений за людиною й не змінюється, тож у нормі це один
  рядок; таблиця замість колонки потрібна, щоб номер вибулого учня не можна було
  тихо перевикористати для нового і зіпсувати історію заднім числом.

### 4.4 Зарахування
`enrollments(student_id, class_id, from_date, to_date, status)` — переведення між
класами й відрахування стають історією, а не перезаписом поля.

### 4.5 Персонал
`staff_profiles` (категорія, стаж, предмет), `staff_awards`,
`teaching_assignments(teacher_id, subject_id, class_id, period_id)` — джерело
скоупів «свій предмет у своєму класі».

### 4.6 Розклад
`schedule_templates` (тижневий шаблон), `schedule_proposals` (пропозиції на
апрув), `lessons` (матеріалізовані на конкретну дату: тема, ДЗ,
`scheduled_teacher_id`, `conducted_by_teacher_id`, `substitution_reason`,
`status`), `homework`.

### 4.7 Присутність
`scan_events` (сирі події, ідемпотентні за `external_event_id`),
`presence_intervals`, `attendance_records(lesson_id, student_id, status, source,
overridden_by, overridden_at)`, `absence_excuses`.
Первинні події зберігаються окремо від висновків — інакше перерахувати
відвідуваність після виправлення правил неможливо.

### 4.8 Оцінки
`grading_scales`, `grading_scale_levels` (код, підпис, порядок, числовий
еквівалент для аналітики), `grade_categories`, `grade_entries`,
`grade_revisions`, `grade_comments`.

Категорії-сіди: поточна, **тематична**, контрольна робота, **діагностична
робота**, ведення зошита, семестрова, коригування, річна, ДПА. Категорії — дані,
тому директор додає свої без релізу.
Три системи оцінювання (галочки 1-2, літери 3-4, 12 балів 5-9) — це три записи
в `grading_scales`, а не три гілки в коді.

### 4.9 Модерація
`moderation_items(entity_type, entity_id, state, submitted_by, reviewed_by,
rejection_reason, submitted_at, reviewed_at)`.

### 4.10 Комунікація
`conversations`, `conversation_participants`, `messages` (вміст зашифрований),
`message_receipts`.

### 4.11 Психолог і корекційні заняття
`support_sessions` (індивідуальні / групові), `support_session_participants`,
`support_notes` (зашифровані, окремий дозвіл, читання логується).
Факт заняття видно адміну для звітності; зміст нотаток — ні.

### 4.12 Робочий час
`staff_presence_intervals` (зі сканів), `lesson_conduct_records` (академічні
години з фактично проведених уроків), `work_period_summaries`.

### 4.13 Інтеграції
`kitchen_orders`, `kitchen_balance_cache`, `webhook_deliveries`,
`integration_audit`.

### 4.14 Класний журнал
`class_remarks` (зауваження за перевірку журналів) і `safety_briefings`
(бесіди-інструктажі): автор, дата, клас, текст, `acknowledged_at`.

Видимість — вчитель і вищі ролі. Батьки й учні цих записів не бачать: це
внутрішній контроль роботи персоналу, а не комунікація з родиною.
`acknowledged_at` дає вчителю підтвердити ознайомлення — інакше «я цього не
бачив» неможливо спростувати.

### 4.15 Система
`audit_logs`, `sensitive_access_logs`, `outbox`, `notification_deliveries`,
`export_jobs`, `app_settings`.

`app_settings` тримає те, що школа крутить без релізу: час очікування перед
сповіщенням «не прийшов», поріг низького балансу, межі рівня навченості, термін
зберігання даних випускника.

## 5. Ключові потоки

### 5.1 Оцінка з модерацією
Вчитель ставить оцінку → публікується миттєво, батьки бачать.
Коментар → `moderation_items(pending)`, батьки не бачать, вчитель бачить свій із
позначкою «на перевірці». Схвалення → подія в `outbox` → Telegram/email.
Відхилення → обовʼязкова причина, повернення вчителю.
Через 24 години без розгляду — нагадування модератору. Автосхвалення немає.
Редагування вчителем — 48 годин; пізніше лише за дозволом і з причиною.
Кожна зміна — рядок у `grade_revisions` і `audit_logs`.

### 5.2 Відвідуваність зі сканів
Сканер → `apps/api` (HMAC, ідемпотентність за `event_id`) → `scan_events` →
перерахунок `presence_intervals` → `Н` на уроки, що не перетинаються з жодним
інтервалом. Ручне перевизначення не затирає автоматичне: `source` стає `manual`,
автор видимий у журналі.
Окремий cron у налаштований час шукає тих, хто не зʼявився взагалі, і шле подію
батькам.

### 5.3 Розклад
Вчитель складає слоти → валідація трьох конфліктів (клас зайнятий, вчитель
зайнятий, кабінет зайнятий) → `schedule_proposals` → апрув адміна →
матеріалізація в `lessons` з урахуванням канікул і свят.
Заміна не переписує урок, а заповнює `conducted_by_teacher_id` — звіт «скільки
уроків предмета було і хто вів» рахується без окремої підсистеми.

## 6. Шифрування і чутливі дані

Шифруємо (pgcrypto, ключ у Supabase Vault, окремо від бази): `messages.content`,
`student_health_notes`, `support_notes`.

Не шифруємо те, за чим потрібні фільтри й статистика (§4.3). Зашифрована
колонка, за якою треба фільтрувати, — помилка проєктування, а не задача для
індексу.

**Пошук по повідомленнях.** Рішення — пошуку немає. Про зворотність чесно:
ключ у нас, тому додати пошук пізніше технічно можливо (розшифрувати й
переіндексувати весь масив разовою задачею) — це дорого, але не незворотньо.
Тому blind index зараз не робимо: корисний індекс — це HMAC кожного токена в
окремій таблиці, а він за побудовою зливає частотність слів. Платити приватністю
за функцію, яку ти не замовляв, немає сенсу.

Що робимо натомість для захисту дітей: перевірка на стоп-слова **до**
шифрування, у памʼяті. Зберігається лише прапорець `flagged` і категорія —
адмін отримує сигнал і відкриває конкретну розмову. Це закриває реальну потребу
модерації без зберігання відкритого тексту.

## 7. Сповіщення

Канали: Telegram (основний) і email через Resend. SMS не робимо.

- `outbox` → QStash → ендпоінт доставки → `notification_deliveries`.
- **Ідемпотентність**: `unique (event_id, channel, target)`. Ретрай QStash
  впирається в конфлікт і не надсилає вдруге. Розраховуємо на at-least-once від
  черги й дедуплікуємо самі.
- `notification_preferences(telegram_link_id, event_type, enabled)` + тихі години.
- Критичні події («дитина не прийшла в школу») ігнорують тихі години й дайджест.

Події: вхід і вихід зі школи, не зʼявився, нова оцінка, схвалений коментар,
нове повідомлення, зміна розкладу або заміна, нове ДЗ, низький баланс буфету,
запрошення в систему, нагадування модератору.

## 8. Інтеграції

**Сканер** — власна система замовника, контракт узгоджено:
`docs/integrations/scanner-contract.md`. Webhook із HMAC-підписом, ідентифікатор —
номер QR картки, напрямок обчислює сканер чергуванням. Starland — джерело істини
про людей; сканер оперує лише номерами й за потреби читає довідник через
read-only ендпоінт. Обовʼязкова вимога до сканера — щодобове скидання стану
присутності о 03:00; на нашому боці — трактування першого `out` доби без `in` як
входу з позначкою розбіжності.

**Кухня** — окрема готова система. Правила з розділу 10 старого документа
лишаються чинними: найвужчий можливий токен, код лише в `portal` і `api`,
зворотний виклик — окремий HMAC-підписаний webhook, що вміє тільки оновити
статус замовлення. Баланс — джерело істини на боці кухні, ми кешуємо останнє
значення для порогового сповіщення. Дублювати гроші в двох базах означає
гарантовані розбіжності.

**Календар** — персональний ICS-фід з токеном у URL, що відкликається з профілю.

---

## 9. Безпека й аудит

RLS на всіх таблицях. Аудит на зміни оцінок, відвідуваності, ролей, дозволів,
доступ до чужих профілів. `sensitive_access_logs` — лог **на читання** медичних
і психологічних записів. Фізичних видалень немає ніде. Персональні дані не
потрапляють у Sentry й логи — лише ідентифікатори.

---

## 10. Звіти й експорт

Власні формати, без офіційних бланків МОН. Шар генерації відокремлений від
логіки звіту, щоб підмінити шаблон пізніше без переписування.
Звіти: відвідуваність (школа / клас / учень за період), проведені уроки по
вчителях і предметах із замінами, рівень навченості, табель учня, робочий час
персоналу.
Великі експорти — `export_jobs` із прогресом, результат у приватний бакет,
посилання з коротким TTL. Ліміт часу функції Vercel вимагає різати на чанки.

## 11. Поза скоупом

Офлайн-режим, мобільний застосунок, AI-модуль, SMS, двосторонній чат у Telegram,
пошук по повідомленнях, OAuth-синхронізація з Google Calendar, офіційні бланки
звітності, ІПР та інклюзивна документація.

## 12. Відкриті питання

Лишилось одне: **перелік методів API кухні й тип авторизації**. Система готова,
але її контракт нам ще не переданий. До Т4 працюємо за припущенням: створення й
скасування замовлення, читання балансу, історія покупок, API-ключ у заголовку.
Якщо реальність відрізняється — міняється лише пакет `integrations/kitchen`,
решта системи цього не помічає.

Решту закрито: сканер (розділ 8), медичні дані (4.3), типи оцінок (4.8),
зауваження за перевірку журналів (4.14).
