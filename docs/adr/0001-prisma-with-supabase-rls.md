# ADR 0001: Prisma Migrate поверх Supabase RLS — версія, shadow database, analytics

**Статус:** Прийнято (Task 2, 2026-07-31)

## Контекст

Стек (розділ 1 `CLAUDE.md`) фіксує Prisma як ORM і Supabase Postgres з RLS.
Перша ж міграція (`app_users` + `app_users_self_select`, Task 2) наштовхнулась
на дві незалежні проблеми інструментарію, які впливають на кожну наступну
міграцію з RLS-політикою, а не лише на цю одну:

1. На момент виконання задачі `pnpm add prisma` резолвить `7.9.1` — мажорна
   версія прибрала `datasource { url = env(...) }` у `schema.prisma` на
   користь окремого `prisma.config.ts` (`P1012`). Це той самий клас
   несумісності, що й з `typescript` у Task 1: інструментарій пішов далі за
   те, що очікує план.
2. `prisma migrate dev` перед застосуванням реплеює всю історію міграцій у
   тимчасовій shadow database, щоб виявити дрейф. Наша RLS-політика
   викликає `auth.uid()` — функцію, яку визначає Supabase/GoTrue лише у
   реальній базі проєкту. У щойно створеній shadow database схеми `auth`
   немає взагалі, тож `migrate dev` падає з `P3006: schema "auth" does not
   exist`. Це відома взаємодія Prisma + Supabase (Prisma issues #17313,
   #18881, #26231, обговорення #17035; офіційний Supabase Prisma
   troubleshooting guide прямо попереджує не звертатись до керованих
   Supabase схем із міграцій Prisma, але RLS-політики на `auth.uid()` —
   вимога самого проєкту, розділ 3 `CLAUDE.md`).

Додатково: `supabase start` стабільно падав на health-check контейнерів
`logflare`/`vector` (сервіс аналітики), відтворено двічі поспіль навіть
після повного локального кешу образів.

## Рішення

1. **Пінимо `prisma` і `@prisma/client` на `^6.19.3`** (останній мажор 6.x) —
   `datasource.url` у `schema.prisma` й далі підтримується, схема плану
   лишається дослівною.
2. **Shadow database — окрема, persist-нута, з підготовленим стабом
   `auth.uid()`.** `packages/db/prisma/schema.prisma` отримав
   `shadowDatabaseUrl = env("SHADOW_DATABASE_URL")` (додатково до
   `url`, не замість). Стаб живе в `packages/db/prisma/bootstrap/shadow-bootstrap.sql`
   (не в `prisma/sql/` — той каталог зарезервований під Prisma TypedSQL,
   один запит на файл, а це DDL; майбутні задачі плану вже claim'ять
   `prisma/sql/*.sql` під TypedSQL-запити) (ідемпотентний: `create schema if not exists auth` +
   `create or replace function auth.uid() returns uuid ... select null::uuid`)
   і застосовується командою `pnpm --filter @starland/db run shadow:bootstrap`
   (`packages/db/scripts/bootstrap-shadow-db.mjs`): створює базу
   `prisma_shadow` на тому ж Postgres-сервері, якщо її ще немає, і накатує
   SQL-файл через `prisma db execute`. Реального `auth.uid()` (визначення
   GoTrue в базі `postgres`) цей стаб не чіпає — окрема база, окреме
   з'єднання.
3. **`[analytics] enabled = false`** у `supabase/config.toml` — аналітика
   не потрібна жодному завданню в межах Т1, а її контейнери — джерело
   нестабільного локального старту.

## Наслідки

- Кожен новий чекаут або скинутий Docker-том Supabase вимагає одноразово
  `pnpm --filter @starland/db run shadow:bootstrap` перед першим
  `prisma migrate dev`. Скрипт ідемпотентний — безпечно ганяти повторно.
- Будь-яка майбутня RLS-політика, що звертається до `auth.*` (наприклад,
  `auth.jwt()`), потребує розширення `shadow-bootstrap.sql` відповідним
  стабом — інакше та ж `P3006` повториться для нової міграції.
- Інші керовані Supabase схеми (зокрема `storage`, яка утримує `storage.buckets`)
  також відсутні в shadow database. Міграції, що звертаються до таких схем
  (наприклад, створення приватних бакетів), потребують умовної перевірки наявності таблиці,
  обгорнутої в `do $$ if exists ... then ... end if; $$`. Це не дійсне перевір без
  гарантії на реальних базах Supabase — дані schema завжди присутні там,
  `if` завжди істина, виконання завжди відбувається. Ідемпотентність забезпечується
  `on conflict (id) do nothing` або подібними механізмами.
- Версію Prisma 6.x тримаємо свідомо; апгрейд на 7.x — окреме рішення (нове
  ADR), бо вимагає міграції на `prisma.config.ts` і, ймовірно, перегляду
  цього ADR.
- Якщо колись керування RLS-міграціями перенесеться з Prisma Migrate на
  власний інструментарій Supabase CLI (`supabase migration new` /
  `supabase db push`) — весь цей ADR стає нерелевантним: у Supabase CLI
  немає окремої shadow database з такою проблемою, вона працює проти копії
  реальної схеми проєкту. Такий перехід — привід переглянути й, скоріш за
  все, закрити цей ADR, а не доповнювати.

## Два підключення: `postgres` для міграцій, `app_runtime` для рантайму (Task 2c)

### Проблема

`DATABASE_URL` підключає Prisma як роль `postgres`. У локальному Supabase
`postgres` не є справжнім суперкористувачем (`rolsuper = f`), але має
`rolbypassrls = t` — а це саме той атрибут, який PostgreSQL перевіряє, щоб
вирішити, застосовувати політики RLS чи ні. Наслідок: RLS-політика
`app_users_self_select` із Task 2 реальна й увімкнена, але для коду
застосунку — якщо він теж підключається через `DATABASE_URL` — вона
**ніколи не спрацьовує**: `prisma.appUser.findMany()` бачить усі рядки
незалежно від політики. Захист, збудований у Task 2, був декоративним.

### Рішення

Два підключення з різним призначенням і різними правами:

1. **`DATABASE_URL` (`postgres`)** — тільки для `prisma migrate` і
   написаного вручну SQL міграцій. Обходить RLS свідомо: міграція мусить
   мати змогу створити RLS-політику та наповнити довідники до того, як
   будь-яка політика почне щось приховувати.
2. **`APP_DATABASE_URL` (`app_runtime`)** — єдине підключення, яке
   дозволено використовувати коду застосунку (`appPrisma` з
   `packages/db/src/user-context.ts`). Роль створена з
   `nosuperuser nobypassrls noinherit`:
   - `nosuperuser`/`nobypassrls` — щоб RLS застосовувалась завжди, без
     винятків;
   - `noinherit` — щоб сама базова роль з'єднання не мала жодних прав на
     таблиці `public`, доки транзакція явно не візьме на себе роль
     `authenticated` (`set local role authenticated`). Це навмисно
     "fail closed": з'єднання, яке з якоїсь причини не пройшло через
     `withUserContext`, не бачить нічого — не тому, що RLS відфільтрував
     рядки, а тому, що йому взагалі відмовлено в праві на `select`.
   - Права на таблиці `app_runtime` отримує не напряму, а через
     `grant authenticated to app_runtime` (членство в штатній ролі
     Supabase) — щоб не переписувати гранти під кожну нову таблицю; сама
     ж роль `authenticated` отримує явний `grant` на існуючі таблиці плюс
     `alter default privileges ... for role postgres`, бо таблиці,
     створені роллю `postgres` (не `supabase_admin`), не отримують
     дефолтних прав Supabase автоматично.
   - Пароль ролі — секрет: задається окремою командою поза текстом
     міграції (`alter role app_runtime password '...'`), живе тільки в
     `.env` (gitignored); `.env.example` містить лише імена змінних.

### Чому контекст користувача — транзакційний, а не на рівні з'єднання

`APP_DATABASE_URL` іде через пулер, і одне фізичне з'єднання
обслуговує запити різних користувачів послідовно. `withUserContext`
встановлює особу виключно всередині однієї транзакції:

- `set_config('request.jwt.claims', ..., true)` — третій аргумент `true`
  (`is_local` у термінах `set_config`) робить значення дійсним лише в межах
  поточної транзакції, воно скидається на `COMMIT`/`ROLLBACK`;
- `set local role authenticated` — так само транзакційний, на відміну від
  `set role`, яке лишається на все з'єднання.

Обидва — навмисно, а не за замовчуванням: якби замість цього
використали `set_config(..., false)` (сесійний) або `set role` (сесійне),
особа й підвищені права одного користувача пережили б `COMMIT` і
дісталися б наступному запиту на тому самому фізичному з'єднанні —
класична дірка пулених з'єднань. Це перевірено окремим тестом
("does not leak the context into the next transaction" у
`packages/db/test/user-context.test.ts`), і саме він ловить регресію,
якщо колись `set local` випадково заміниться на сесійний варіант.

### Наслідки

- Кожна доменна операція, що читає/пише `app_users` (і будь-яку майбутню
  таблицю з RLS), мусить іти через `appPrisma` + `withUserContext`, не
  через `prisma` з `packages/db/src/client.ts` — останній лишається
  привілейованим і призначений тільки для міграцій та інфраструктурних
  скриптів.
- Кожна нова таблиця автоматично отримує грант для `authenticated`
  завдяки `alter default privileges`, але це не звільняє від обов'язку
  ввімкнути RLS і написати політику в тій самій міграції (розділ 2,
  правило 1 `CLAUDE.md`) — грант відкриває видимість таблиці, а не рядків.
- Task 3 (тестовий харнес RLS) переносить логіку створення користувача
  `auth.users`/`app_users`, тимчасово продубльовану в
  `user-context.test.ts`, у спільний `rls-harness.ts`.

## Виняток із правила 1a: SECURITY DEFINER-функція-обгортка над таблицею без політик читання (Task 7, Task 9)

### Проблема

Правило 1a у `CLAUDE.md` забороняє RLS-політиці викликати функцію з
аргументом, що змінюється по рядках (`has_scope(x, y)` — можна,
`some_fn(id)` там, де `id` — колонка таблиці, що фільтрується, — не можна),
бо планувальник тоді не може обчислити множину доступу один раз на запит.

`enrollments` (Task 7, `20260801100515_fix_students_guardians_rls_scope`)
свідомо лишена з увімкненим RLS і без жодної політики читання — це
default-deny, а не тимчасовий недогляд: `person_cards`,
`student_measurements`, `guardian_persons`, `guardianships` отримали те
саме навмисно, до появи задачі, яка визначить їм власний скоуп. Наслідок:
**жоден** прямий підзапит до `enrollments` з тіла чужої RLS-політики
(`students_read`, `classes_read`) не може повернути жодного рядка для
звичайного автентифікованого користувача — не через логічну помилку умови,
а тому що сам `select` на `enrollments` заборонений RLS ще до того, як
умова `where` встигає щось відфільтрувати. Тобто "просто перепиши як
`IN (SELECT ... FROM enrollments WHERE ...)` без функції" тут не працює
в принципі, на відміну від звичайного випадку, який 1a описує.

Це вдарило двічі:
- Task 7 (`20260801100515_fix_students_guardians_rls_scope`):
  `student_visible_via_class_scope(p_student_id uuid)`.
- Task 9 (`20260801215402_students_read_teaching_assignment_security_definer`):
  `student_visible_via_teaching_assignment_scope(p_student_id uuid)` —
  той самий підхід, той самий привід, при виправленні регресії, яку
  дослівне копіювання SQL з плану внесло в `students_read`.

### Рішення

Обидві функції — `stable security definer set search_path = public`,
беруть єдиним аргументом `p_student_id uuid` (значення, що змінюється по
рядках — саме те, що 1a у загальному випадку забороняє), і всередині
роблять `select exists (... from enrollments e where e.student_id =
p_student_id and ...)`. `SECURITY DEFINER` — єдина причина, чому цей
`select` взагалі щось бачить: функція виконується з правами власника
(обходить RLS `enrollments` зсередини), а не з правами користувача, що
викликав політику.

**Явне звуження правила 1a**: виклик `SECURITY DEFINER`-функції з
рядково-змінним аргументом у тілі RLS-політики є прийнятним винятком,
коли одночасно виконуються обидві умови:

1. Функція — це `exists`-перевірка одного факту про один рядок (lookup),
   а не довільна бізнес-логіка;
2. Ціль запиту всередині функції — таблиця з увімкненим RLS і без жодної
   політики читання для викликача, тобто альтернативи "переписати без
   функції" не існує: сирий підзапит у тілі політики не поверне жодного
   рядка незалежно від того, наскільки правильна умова `where`.

Якщо колись `enrollments` (чи інша таблиця в такому ж стані) отримає
власну політику читання, яка й сама виражається як "входження в множину,
обчислену раз на запит" (як того вимагає 1a для звичайного випадку) —
відповідну `SECURITY DEFINER`-обгортку варто прибрати й повернутись до
прямого підзапиту, бо тоді виняток більше не потрібен.

### Наслідки

- Обидві функції (`student_visible_via_class_scope`,
  `student_visible_via_teaching_assignment_scope`) лишаються без
  окремого перф-тесту на реалістичному обсязі, як того буквально вимагає
  1a для кожної такої політики. Свідомий компроміс: паттерн вже
  повторився двічі з ідентичною формою (`exists`-lookup через
  `SECURITY DEFINER` на одну й ту саму пару таблиць), тому дешевше й
  надійніше зафіксувати межу винятку тут, ADR-ом, ніж писати perf-suite
  під кожен повтор. Якщо цей паттерн з'явиться втретє для нової таблиці —
  perf-тест на реалістичному обсязі стає обов'язковим, а не
  опціональним: два повтори без вимірювання — прийнятний ризик,
  три — вже статистика, яку варто перевірити.
- Будь-яка майбутня RLS-політика, що потребує того самого прийому (нова
  таблиця без політик читання, до якої треба дістатись із чужої
  політики), може посилатись на цей розділ ADR замість того, щоб заново
  обґрунтовувати відхилення від 1a.
