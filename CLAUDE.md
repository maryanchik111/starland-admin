# CLAUDE.md — правила роботи агентів у проєкті Starland

Цей файл читає кожен агент перед будь-якою дією. Правила тут мають пріоритет над
загальними звичками моделі. Якщо правило суперечить прямій вказівці людини —
перемагає людина, але агент зобовʼязаний вголос сказати, яке правило порушується.

---

## 0. Контекст проєкту

- **Starland** — приватна школа (1–9 класи), Україна. Система: адмінка школи +
  портал для батьків/учнів.
- **Single-tenant**: одна школа. Поля `school_id` в схемі немає. Друга школа = окремий деплой.
- Команда: соло-розробник + AI-агенти. Це означає: код має бути нудним, читабельним
  і покритим тестами, бо його нікому ревʼювити, крім агентів.
- Джерела істини по вимогах (читати перед роботою, у цьому порядку):
  1. `docs/specs/` — затверджені специфікації (що будуємо),
  2. `docs/plans/` — плани реалізації (як будуємо, покроково),
  3. `docs/adr/` — архітектурні рішення та їх причини,
  4. `starland-business-logic.md` — початкові рішення по інфраструктурі й безпеці.
- Якщо вимога відсутня в цих файлах — **її не існує**. Не вигадувати. Питати або
  ставити `TODO(question): ...` і виносити в кінець відповіді.

## 1. Стек — фіксований, змінюється лише через ADR

| Шар | Вибір |
|---|---|
| Монорепо | pnpm workspaces + Turborepo |
| Frontend + API | Next.js (App Router), Server Actions для мутацій |
| БД | Supabase Postgres + RLS (регіон EU) |
| ORM | Prisma (через Supabase Connection Pooler) |
| Auth | Supabase Auth (passkeys/TOTP для персоналу) |
| Realtime | Supabase Realtime |
| Файли | Supabase Storage, приватні бакети, signed URL ~5 хв |
| Фонові задачі | BullMQ + Upstash Redis |
| Валідація | Zod на кожній межі (вхід Server Action, webhook, зовнішній API) |
| Тести | Vitest (unit/integration), Playwright (e2e) |
| Помилки | Sentry |

Застосунки: `apps/admin` (директор/адмін/вчителі/психолог), `apps/portal`
(батьки/учні), спільні пакети в `packages/*`.

Хочеш інший інструмент — спочатку ADR у `docs/adr/`, потім код. Ніяких «я взяв
бібліотеку X, бо зручніше».

## 2. Залізні правила безпеки (порушення = зупинка роботи)

1. **RLS увімкнено на кожній таблиці.** Таблиця без policy не потрапляє в мердж.
   Кожна міграція, що створює таблицю, у тому ж файлі створює й політики.
1a. **RLS-політика не викликає функцію з аргументом, що змінюється по рядках.**
   Доступ виражається як перевірка входження в множину, яку планувальник
   обчислює один раз на запит: `class_id IN (SELECT ... FROM user_scopes(...))`.
   Функції для RLS — `STABLE` + `SECURITY DEFINER` (інакше рекурсія на самих
   таблицях доступів). Кожна така політика має перф-тест на реалістичному обсязі.
1b. **Кожна доставка сповіщення ідемпотентна**: `unique (event_id, channel, target)`.
   Черга гарантує at-least-once, дедуплікацію робимо ми, а не сподіваємось на неї.
2. **`SUPABASE_SERVICE_ROLE_KEY` ніколи не потрапляє в клієнтський бандл** і
   ніколи не використовується в `apps/portal`. Привілейовані операції — через
   Postgres-функції `SECURITY DEFINER` з явною перевіркою прав усередині.
3. **Жодних секретів у репозиторії.** Тільки `.env.example` з іменами змінних.
4. **Кухонна інтеграція живе фізично тільки в `apps/portal`.** В `apps/admin`
   не має бути навіть імпорту цього коду.
5. **Кожен вхідний webhook перевіряється HMAC-підписом**, не IP і не доменом.
6. **Ніяких сирих SQL-запитів в обхід RLS** з кодом застосунку. Виняток —
   міграції та явно позначені `SECURITY DEFINER` функції з ревʼю.
7. **Персональні та медичні дані не логуються** — ні в Sentry, ні в консоль, ні в
   `audit_logs.details`. У логах — тільки ідентифікатори.
8. **Агент ніколи не підключається до продакшн-БД** і не запускає міграції на
   проді. Тільки локальний Supabase / staging.

## 3. Інваріанти доменної логіки

Це не «побажання», це поведінка, яку ламати не можна. Кожен інваріант має бути
покритий тестом.

- **Оцінки не видаляються фізично.** Тільки `deleted_at` + причина + автор.
- **Кожна зміна оцінки, відвідуваності, доступу, ролі — запис в `audit_logs`**
  (хто, коли, що, старе значення, нове значення).
- **Вікно редагування оцінки вчителем — 48 годин.** Після цього змінює лише
  користувач із відповідним дозволом і **обовʼязково з коментарем-причиною**.
- **Вчитель діє тільки в межах своїх пар предмет+клас.** Перевірка — і в RLS, і в
  доменному шарі, не тільки в UI.
- **Коментарі до оцінок і зауваження проходять модерацію** перед показом батькам:
  стан `pending → approved | rejected`. Сама оцінка публікується одразу.
- **Відсутність (`Н`) ставиться автоматично** з даних сканування на вході, але
  завжди може бути перевизначена людиною вручну — з фіксацією, хто перевизначив.
- **Прозорість для батьків**: якщо запис востаннє змінив не автор, UI це показує.
- **Психологічні записи мають окремий рівень доступу**, а не «адмін бачить усе за
  замовчуванням». Доступ до них логується окремо (лог на читання, не тільки запис).
- **Персональний дозвіл (`permission_grants`) не існує без сліду**: обовʼязкові
  `granted_by`, `reason`, `expires_at`; відкликання — `revoked_at`, не `DELETE`;
  створення й відкликання пишуть `audit_logs`. Екран «ефективні права людини»
  показує кожен дозвіл разом із походженням (з якої ролі або з якого гранту, ким
  і коли виданий) і будується з тієї самої проєкції, що виконує перевірку, —
  щоб UI не міг розійтися з реальним доступом.
- **Належність родини до учня перевіряється на сервері в кожному запиті**, а не
  береться з клієнта чи з клейма в токені. `student_id` у запиті — це намір, а не
  дозвіл.

## 4. Правила бази даних

- Іменування: таблиці — `snake_case`, множина (`students`, `grade_entries`).
  Колонки — `snake_case`. FK — `<entity>_id`.
- Кожна таблиця має: `id uuid pk default gen_random_uuid()`, `created_at`,
  `updated_at`. Де є видалення — `deleted_at`, а не `DELETE`.
- **Шифруємо лише вільний текст.** Поля, за якими треба фільтрувати, сортувати
  чи рахувати статистику (група здоровʼя, фізкультурна група, коди алергій) —
  структуровані довідники без шифрування. Зашифрована колонка, за якою потрібен
  фільтр, — це помилка проєктування, а не задача для індексу.
- Довідники (типи оцінок, шкали, причини відсутності, типи сповіщень) — **дані в
  таблицях, не enum у коді**, бо директор має редагувати їх з адмінки.
  Enum у Postgres — лише для того, що не змінюється без міграції коду.
- Історичні дані — окремі таблиці-вимірювання (`student_measurements`), а не
  перезапис полів. «Порівняння початок/кінець року» неможливе без історії.
- Міграції: тільки через `prisma migrate`. **Застосовану міграцію не редагувати** —
  писати нову.
- Кожна нова таблиця отримує: RLS-політики + тест на RLS (позитивний і
  негативний сценарій для кожної ролі).

## 5. Правила коду

- TypeScript strict. `any` заборонено; якщо інакше не виходить — `unknown` + Zod.
- **Бізнес-логіка не живе в React-компонентах і не живе в Server Action.**
  Server Action = валідація входу (Zod) → виклик доменної функції → маппінг
  результату. Домен — у `packages/domain/`, тестується без Next.js.
- Файл більший за ~300 рядків — сигнал розділити. Компонент, що робить і
  завантаження даних, і бізнес-правила, і рендер — розділити.
- Помилки — типізований результат (`Result<T, DomainError>`), не `throw` для
  очікуваних ситуацій. `throw` — тільки для дійсно виняткових станів.
- Дати й час: у БД `timestamptz`, у коді — UTC, у UI — `Europe/Kyiv`. Ніяких
  локальних дат у бізнес-логіці.
- Мова: код, коментарі, імена, назви колонок — англійською. UI-тексти —
  українською, **тільки через словник** `packages/i18n`, не хардкодом у JSX.

## 6. Правила UI (з бізнес-вимог)

- **Будь-яка згадка людини або сутності в інтерфейсі — клікабельна.** Імʼя в
  логах, у звіті, у журналі, у чаті → веде на `/profile/[id]` (або відповідну
  сторінку сутності). Це вимога замовника, не деталь оформлення.
- Кожен екран існує в двох режимах: `view` і `edit`, залежно від дозволів
  користувача. Немає дозволу — елемент не рендериться взагалі, а не
  «рендериться і падає на сервері».
- Порожні стани, стани завантаження й помилки проєктуються разом з екраном, а не
  дописуються потім.

## 7. Робочий процес агента

1. **Спочатку скіл, потім дія.** Нове функціональне завдання → `brainstorming` →
   `writing-plans` → `test-driven-development`. Баг → `systematic-debugging`.
2. Не починати кодити без файлу плану в `docs/plans/`. Один крок плану = один
   логічно завершений коміт.
3. **TDD обовʼязковий** для доменної логіки, RLS-політик і будь-чого з розділу 3.
   Тест спочатку, він має впасти, потім код.
4. Перед заявою «готово» — запустити тести/лінт/тайпчек і показати вивід.
   Без виводу команди фраза «працює» заборонена.
5. Не робити рефакторинг, про який не просили, в тому ж коміті, що й фічу.
6. Не додавати залежність без потреби, яку не можна закрити 20 рядками свого коду.
7. Після зміни архітектурного рішення — оновити `docs/adr/`.

---

## 8. Definition of Done

Задача готова, коли:

- [ ] Є тест, який падав до зміни й проходить після.
- [ ] RLS-політики створені й покриті негативним тестом (для нових таблиць).
- [ ] Критичні дії пишуть `audit_logs`.
- [ ] Типчек, лінт і тести проходять — вивід показано.
- [ ] UI-тексти — у словнику, не в компоненті.
- [ ] Оновлені `docs/` там, де змінилась поведінка чи архітектура.
- [ ] Немає секретів, `console.log` з ПД і закоментованого коду.

---

## 9. Чого агент не робить ніколи

- Не працює з продакшн-даними.
- Не вимикає RLS, лінт-правило чи тест, щоб «пройшло».
- Не видаляє фізично записи учнів, оцінок, повідомлень, логів.
- Не вигадує вимоги й не «додає корисне» поза скоупом задачі.
- Не пише, що щось працює, не запустивши це.
- Не змінює правила в цьому файлі без прямої вказівки людини.
